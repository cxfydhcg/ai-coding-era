# 核心原则

[English](en/01-core-principles.md) | **简体中文**

## 1. 从“生产代码”转向“交付可信结果”

代码从来不是最终结果。真正的结果可能是减少支付失败、缩短操作时间、避免数据丢失，或让一个业务流程可以被审计。

AI 可以非常快地生成一个看似完整的实现，这反而会放大一个旧问题：团队容易把“代码已经出现”误认为“问题已经解决”。AI 时代的工程过程必须围绕结果建立证据链：需求证据、测试证据、审查证据、发布证据和生产证据。

## 2. 意图必须先于生成

在要求 Agent 修改系统之前，至少应明确：

- 期望产生什么可观察结果；
- 什么内容属于范围内，什么不属于；
- 哪些兼容性、安全性和业务约束不能破坏；
- 用什么方式证明任务完成；
- 谁对关键取舍和发布承担责任。

如果这些问题没有答案，Agent 最容易做出的不是正确实现，而是一个自洽但错误的假设集合。

## 3. 验证能力必须跟上生成能力

当实现吞吐量提升十倍，而审查、测试和生产观察能力不变时，系统只是更快地产生未经验证的变化。

验证应分层：

```text
静态约束 → 单元行为 → 集成边界 → 端到端流程 → 生产观察
```

不同风险的任务不需要相同深度，但每个任务都应在开始前声明最低验证要求。Agent 自己写的测试可以作为证据，不能天然被视为独立证据。

## 4. 有边界的自主性

Agent 应被允许主动检索、分析、提出方案、运行安全验证和发现相邻问题。与此同时，以下动作需要显式授权：

- 扩大当前任务范围；
- 改变产品行为或公共契约；
- 接受安全、隐私、财务或运行风险；
- 修改生产状态；
- 删除仍可能被使用的兼容路径或数据；
- 代表人或组织对外沟通。

原则可以概括为：

> 发现能力不等于决策权限，执行能力不等于发布权限。

## 5. 渐进式上下文，而不是上下文倾倒

Agent 需要足够的上下文，但把整个组织的所有文档一次性加载进去，会增加噪声、过期信息和语义冲突。

更可靠的方式是按任务逐层检索：

1. 读取任务契约和局部规则；
2. 定位相关代码和当前状态文档；
3. 查询相关 backlog、决策记录和历史变化；
4. 只在出现边界问题时扩展到相邻领域；
5. 对冲突信息报告来源与时间，不自行猜测权威答案。

## 6. 一个生命周期状态，一个有效事实源

同一事项可以在生命周期中经过 backlog、需求、实现、当前文档和历史记录，但不应同时存在多个彼此独立的“当前版本”。

```text
发现 → 延后 → 承诺 → 实现 → 生产观察 → 淘汰
```

状态变化时，信息应移动、压缩或被替代，而不是无止境复制。稳定 ID 可以连接各阶段，active canonical record 应保持唯一。

## 7. 证据优先于表达信心

“看起来没问题”“应该可以”和“Agent 很确定”都不是交付证据。好的任务结论应明确区分：

- 已经直接验证的事实；
- 根据现有信息推断的结论；
- 尚未验证的假设；
- 需要人类做出的决定。

这让审查者能够把注意力放在不确定性上，而不是重新检查所有内容。

## 8. 删除是一等工程活动

生成新代码很容易，安全地删除旧代码更难。每个临时兼容层、迁移分支和 feature flag 在进入系统时，就应尽可能记录：

- 为什么存在；
- 谁或什么仍依赖它；
- 满足什么证据后可以删除；
- 谁拥有淘汰决定；
- 删除后如何验证和回滚。

没有淘汰机制的“临时方案”，通常只是没有命名的永久复杂度。
