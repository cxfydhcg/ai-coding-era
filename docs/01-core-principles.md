# 核心原则

[English](en/01-core-principles.md) | **简体中文**

这些是我用来判断流程是否有用的标准。具体动作见[个人流程](02-individual-workflow.md)，不必把原则再变成一套额外审批。

## 先说结果，再谈实现

任务开始前说清楚：要改变什么、哪些不能动、怎样验收、谁负责决定。小修改几句话足够；跨系统、迁移和不可逆操作需要更完整的契约。

## 验证预期行为

测试应该检查需求中的行为。AI 写的测试可能与实现共享错误假设；换一个模型或会话也不自动构成独立验证。关键判断应对照契约、真实样本、领域人员或独立计算结果。

报告时分清已验证、推断和未验证，给出证据，少写“应该没问题”。

## 在授权范围内连续工作

检索、实现和验证可以连续进行，已经授权的常规动作不必反复确认。新的产品取舍、跨系统契约变化、生产操作或不可逆删除，需要相应权限。仓库可以预先授权有边界的相邻修复，发现问题本身不能扩大授权。

## 上下文随任务读取

仓库应保存目标、当前进度、下一步和证据，使换人或换 Agent 后仍能接手。开始时读任务记录、相关规则和代码，结束前写回状态。出现冲突时查明来源和时间，不把全部文档一次塞进上下文，也不默认最新文字最权威。

## 每条信息有归属和退出条件

当前行为、未来工作和历史原因分开存放。状态变化时转移或压缩，避免多份正文各自漂移。临时逻辑引入时写明依赖者和删除条件；发布、升级与备份恢复证据未满足前，不因“代码很旧”而删除。

衡量这些原则是否有效，看返工、遗漏和找上下文的成本是否下降。[研究边界](00-research-foundation.md)解释了为什么不能只看代码量或 AI 使用率。
