# 个人开发流程：把一次改动做完整

[English](en/02-individual-workflow.md) | **简体中文**

我希望 AI 接手明确、可验证的执行工作，自己把注意力放在目标、关键取舍和结果上。任务越含糊，越需要先一起澄清；边界越清楚，越适合连续委托。

## 一个日常循环

```text
确认问题 → 读上下文 → 定义完成 → 小步实现与验证 → 审查发布 → 观察与清理
```

| 步骤 | 做什么 | 何时可以往下走 |
| --- | --- | --- |
| 确认问题 | 看原始反馈、日志或复现，说明想改变的行为。 | 问题真实，且值得现在处理。 |
| 读上下文 | 看相关代码、测试、规则和开放问题。 | 能解释当前行为、影响范围和未知项。 |
| 定义完成 | 写目标、不做什么、约束、验收与权限。 | 换个人也能判断是否完成。 |
| 实现与验证 | 每次改一个可检查的行为，跑最近的有效测试，再看 diff。 | 结果符合预期，失败路径没有被隐藏。 |
| 审查发布 | 核对范围、配置、文档与发布条件。 | 风险有负责人，失败能停止或恢复。 |
| 观察清理 | 看用户与系统结果，回写文档，处理临时逻辑。 | 结果有证据，剩余工作有明确归属。 |

小修改可以在一次会话完成这些步骤，不需要六份文档。复杂任务使用[任务模板](../templates/task-contract.md)。

## 让验收足够具体

下面是一个示例任务：

```text
目标：请求失败时，订单列表显示可重试的错误。
范围：列表加载与错误展示；不改排序或接口。
验收：成功且无订单显示空状态；超时或格式错误显示错误；重试成功后恢复列表。
验证：分别测试三种响应，并检查实际界面的重试流程。
```

这比“优化错误处理”更容易委托，也更容易发现 AI 把解析异常当成空数组的错误实现。

## 根据任务选择配合方式

- **自己做，AI 复核：** 改动很短，或你已熟悉关键细节。
- **边讨论边实现：** 产品语义、设计和风险仍在变化。
- **连续委托：** 范围与验收清楚，验证手段可用。
- **并行调查：** 问题可独立取证；汇总时仍要检查证据是否一致。

并行数量受审查能力约束。任务变大或反复失败时，先检查假设、边界和验证方法，再决定是否继续生成。

## 审查时先问“漏了什么”

主路径之外，按风险检查超时、重复提交、并发、权限、旧数据和恢复。预期结果应来自需求或独立证据，而不只是代码本身。支付、权限和迁移等行为尤其需要这一点。

小批量修改能缩短反馈，便于发现错误后调整方向。[DORA 的小批量实践](https://dora.dev/capabilities/working-in-small-batches/)支持这一方向，但每个任务仍需选择合适的验证深度。

交付说明只需回答：改了什么、验证了什么、还有什么没验证。若生产观察稍后才能完成，写明负责人、信号和检查时间，状态保留为待观察。完成深度见[任务管理](04-task-management.md)，记录维护见[生命周期实践](08-record-lifecycle.md)。
