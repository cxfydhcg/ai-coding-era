# 个人软件开发生命周期

[English](en/02-individual-workflow.md) | **简体中文**

这里的“软件开发”指一个开发者对一个变化从理解问题到生产结果负责的完整过程。AI 可以参与其中每一步，但个人职责不是“把 prompt 发给 Agent”，而是持续维护意图、系统模型、证据和风险边界。

## 生命周期总览

```text
选择问题
  → 恢复上下文
  → 定义任务契约
  → 设计与风险分析
  → 小批量实现
  → 分层验证
  → 自我审查
  → 集成与发布
  → 生产观察
  → 学习与淘汰
```

这不是一次性瀑布流程。每次验证都可能暴露错误假设，让工作回到上下文、契约或设计阶段。关键是每次回退都有新证据，而不是反复生成。

## 0. 选择人与 AI 的协作模式

不要默认所有任务都应该完全委托给 Agent。先根据任务选择模式：

| 模式 | 适合情况 | 人的投入 |
| --- | --- | --- |
| Human-led | 语义高度隐含、代码库非常熟悉、实现很短 | 人直接实现，AI 查询或复核 |
| Pairing | 设计需要持续判断，多个小步骤互相影响 | 人与 Agent 频繁交换假设和证据 |
| Delegated | 任务契约清楚、边界稳定、验证自动化充分 | Agent 连续执行，人审查关键节点 |
| Parallel research | 需要比较方案、定位证据或运行独立检查 | 多路检索，人在汇总时做判断 |

AI 的最佳模式取决于“验证生成结果需要多少成本”，而不只取决于“生成代码需要多少成本”。Microsoft 的多企业现场实验与 METR 的资深维护者实验得到不同结果，也说明工具效果必须按任务环境判断，不能靠感受预设。[研究说明](00-research-foundation.md)

## 1. 选择问题：先确认值得做

输入不应只是“实现某功能”，而应包括真实需求或故障证据：用户反馈、业务指标、复现步骤、运行日志或约束变化。

个人要回答：

- 谁遇到了什么问题？
- 如果什么都不做，会发生什么？
- 成功改变的是用户结果、系统行为，还是内部维护成本？
- 这个问题现在值得处理吗？

AI 让构建低价值功能变得更便宜，却不会让它更有价值。DORA 将 user-centric focus 视为 AI 时代的重要放大能力，因为没有用户目标的速度只会让团队更快走错方向。[DORA: User-centric focus](https://dora.dev/capabilities/user-centric-focus/)

**阶段产物：** 一句 outcome statement，以及支持它的原始证据。

## 2. 恢复上下文：建立当前系统模型

开发者与 Agent 共同读取：

- 当前实现、测试、schema 和接口；
- 局部开发规则与当前状态文档；
- 相关任务、backlog、decision record 和近期变更；
- 生产约束、版本分布、监控和已知事件。

要求 Agent 明确区分：直接观察的事实、从代码推断的行为、未验证假设和冲突信息。个人应验证会改变方案的关键推断。

上下文恢复的目标不是读取整个 repository，而是形成足够准确的局部系统模型，并知道模型的边界。

**退出条件：** 能解释当前行为、变化入口、主要依赖与未知项。

## 3. 定义任务契约：把意图变成可执行边界

使用 [任务契约模板](../templates/task-contract.md) 定义：

- Outcome：可观察结果；
- Scope / non-goals：允许与禁止改变的范围；
- Constraints：产品、兼容、数据、安全、性能与运行约束；
- Acceptance criteria：可被判定的行为；
- Verification：如何获得完成证据；
- Authority：Agent 可以自主做什么，何时必须暂停。

接受标准应尽量在实现前转化为例子、测试 oracle 或可观察指标。TiCoder 的研究支持通过测试驱动的意图澄清帮助人判断 AI 代码是否满足真实意图。[TiCoder study](https://www.microsoft.com/en-us/research/publication/llm-based-test-driven-interactive-code-generation-user-study-and-empirical-evaluation/)

**退出条件：** 另一个开发者或 Agent 不依赖原聊天也能判断什么叫完成。

## 4. 设计与风险分析：决定在哪里改变系统

先做最小必要设计：

- 哪个边界应该拥有这个行为？
- 数据、状态和错误如何流动？
- 现有抽象能否承载，还是正在制造偶然复杂度？
- 什么会失败，失败是否可逆？
- 是否涉及权限、隐私、资金、迁移或公共契约？
- rollout、兼容和 rollback 需要什么？

低风险任务只需几行计划；跨系统或不可逆任务需要 decision record、迁移计划和独立审查。设计深度由风险和未知性决定，不由代码行数决定。

**退出条件：** 有一个可解释的最小方案，关键风险已有验证或缓解方法。

## 5. 小批量实现：让每一步都能验证

把工作拆成可独立理解和检查的增量。推荐循环：

```text
选择一个行为切片
  → Agent/人实现
  → 运行最近、最快的验证
  → 检查 diff 与任务边界
  → 保留证据或修正假设
  → 进入下一个切片
```

小批量降低失败半径、review 成本和 Agent 偏航成本。DORA 将 working in small batches 与交付绩效、快速反馈联系起来，并在 AI 能力模型中再次强调它。[DORA: Working in small batches](https://dora.dev/capabilities/working-in-small-batches/)

实现时不要边发现边无限扩展范围。相邻问题应明确处置为当前修复、backlog、requirement 或非问题。

## 6. 分层验证：从代码证据走到行为证据

验证按照风险逐层增加：

```text
格式与静态规则
→ 单元行为
→ 组件/集成边界
→ 端到端用户路径
→ 安全、性能与兼容检查
→ 目标环境和生产观察
```

AI 可以生成和运行测试，但它写的测试可能复现同一个错误假设。高风险接受标准需要独立 oracle：既有契约、真实样本、另一种实现、人工领域判断或生产信号。

NIST SSDF 建议将安全要求、保护、验证和漏洞响应嵌入现有 SDLC，而不是把安全留到最后。[NIST SSDF](https://csrc.nist.gov/pubs/sp/800/218/final)

## 7. 自我审查：先减少别人的理解成本

提交给团队前，个人应像陌生审查者一样检查：

- diff 是否完整实现 outcome，而不是只完成 prompt；
- 是否存在无关改动、重复抽象或隐藏兼容路径；
- 错误、边界、并发和数据恢复路径是否成立；
- 测试失败时是否真的能捕获目标回归；
- 文档、配置、监控和 rollback 是否同步；
- 哪些结论已验证，哪些只是推断。

AI 适合先做机械和一致性 review；人应保留产品语义、架构代价和风险接受的判断。

**阶段产物：** 小而可解释的 change set、验证摘要、残余风险与 review focus。

## 8. 集成与发布：代码完成不等于价值完成

个人需要与团队流程连接：处理 review 反馈、确认共享 Definition of Done、解决集成冲突、选择 rollout 策略，并记录 release authority。

发布应尽量小、可观察、可停止、可回滚。对于数据库迁移、混合版本客户端和不可逆操作，需要在发布前记录证据门槛，而不是上线后临时判断。

## 9. 生产观察：验证真实世界的结果

观察三类信号：

- **产品结果**：用户任务成功率、采用率、满意度或目标业务指标；
- **系统结果**：错误率、延迟、资源、数据一致性和安全信号；
- **变化质量**：回退、热修、支持请求、意外兼容流量和人工操作。

如果任务无法直接观察生产结果，应明确代理信号、观察窗口和谁负责回来检查。否则“发布后观察”会成为无人执行的愿望。

## 10. 学习与淘汰：让系统恢复简单

完成最后一步：

- 把真实当前行为写回 current-state docs；
- 保存仍影响未来的 decision rationale；
- 把范围外真实问题写入 backlog；
- 删除一次性脚手架和无价值文本；
- 为 feature flag、兼容层和旧数据路径建立 removal gate；
- 将事故或偏差转化为测试、护栏或任务系统改进。

生命周期的目标不是不断增加 artifact，而是让信息进入正确阶段，并在失效后退出。

## 个人的完成标准

一个变化只有在以下问题得到回答时，才称得上可信完成：

1. 我们解决的是哪个可观察问题？
2. 当前实现基于哪些事实和关键假设？
3. 哪些证据证明它满足接受标准？
4. 哪些残余风险由谁接受？
5. 生产环境如何证明结果，失败如何停止或回滚？
6. 未来维护者如何理解当前行为，临时机制何时删除？

AI 可以承担更多执行，但个人的专业能力体现在：选择正确问题、建立正确约束、识别错误证据，并对结果负责。
