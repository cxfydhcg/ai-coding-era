# 个人工作方式

AI 时代的优秀开发者不是“最快接受补全的人”，而是能够把模糊问题转化为清晰任务、让 Agent 高效执行，并对最终行为负责的人。

## 个人角色的变化

一个人与 Agent 协作时，通常同时承担四种责任：

| 责任 | 关键问题 |
| --- | --- |
| 意图负责人 | 我们真正要改变的结果是什么？ |
| 系统设计者 | 哪些边界、约束和长期代价必须考虑？ |
| 证据审查者 | 有什么证据证明实现正确？ |
| 运行责任人 | 发布后如何观察、回滚和收尾？ |

代码可以主要由 Agent 产生，但这四项责任不能因为代码来源改变而消失。

## 每个任务开始前

先写一个短任务契约，而不是直接描述想要的代码。最小内容包括：

- **Outcome**：用户或系统能够观察到的结果；
- **Scope**：允许修改的范围和明确不做的内容；
- **Constraints**：兼容、安全、性能、数据与产品约束；
- **Acceptance**：可以判断完成与否的标准；
- **Verification**：必须运行的检查以及人工验证；
- **Authority**：哪些决定 Agent 可以自行做，哪些必须回来询问。

几分钟的定义通常能避免数小时的错误实现。

## 与 Agent 协作的推荐循环

### 1. 先让 Agent 恢复上下文

要求它读取局部规则、相关实现、测试和历史记录，并陈述它对系统当前行为的理解。不要把一个未经验证的设计直接当作事实输入。

### 2. 让计划暴露假设

计划最有价值的部分不是步骤数量，而是它揭示了哪些假设、依赖和风险。对低风险任务可以很短；涉及数据迁移、公共 API 或生产兼容时，计划必须更具体。

### 3. 在明确边界内实现

允许 Agent 连续完成可逆的局部修改和验证。遇到下列情况应暂停：产品语义不明确、需要扩大范围、发现敏感信息、需要破坏性操作，或证据与任务假设冲突。

### 4. 审查 diff 背后的行为

不要只问“代码是否漂亮”。还要问：

- 是否真的解决了任务定义的结果；
- 是否悄悄改变了其他行为；
- 错误路径、边界值和并发情况如何；
- 测试是否只验证了实现细节；
- 有没有增加不必要的抽象或兼容层；
- 文档和运行方式是否同步改变。

### 5. 关闭反馈循环

任务合并或发布后，记录真实结果。生产行为与假设不同，就更新当前文档、任务系统或淘汰条件。完成不等于代码合并；完成意味着预期结果已经获得与风险相称的证据。

## 个人应培养的能力

- **问题拆解**：把目标拆成可独立验证的变化，而不是大量细碎指令。
- **系统阅读**：能够验证 Agent 对代码、数据和运行环境的理解。
- **约束表达**：把隐性经验写成局部、可执行、可维护的规则。
- **测试设计**：优先验证行为和风险，而不是追求数字覆盖率。
- **判断不确定性**：知道何时继续、何时取证、何时请领域负责人决定。
- **删除能力**：能识别过时文档、重复抽象和已经满足淘汰条件的代码。

## 个人反模式

- 把 prompt 当作 requirement，把生成结果当作完成。
- 同时让 Agent 修改大量无关区域，最后靠肉眼寻找意外变化。
- 因为测试是绿色的，就忽略测试是否覆盖真实业务风险。
- 在聊天中做长期决策，却不把结论写回稳定的信息源。
- 接受自己无法解释的代码，只因为它能运行。
- 不断增加新层来修补问题，却从不删除旧路径。

## 一个简单的每日自检

在提交 AI 参与的变化前，回答五个问题：

1. 我能用一句话说明这次变化的用户或系统结果吗？
2. Agent 做出的关键假设有哪些，我验证了吗？
3. 哪项证据最能证明它工作，哪项风险尚未覆盖？
4. diff 中是否包含任务之外的变化？
5. 未来维护者能从 repository 理解当前行为与关键原因吗？
