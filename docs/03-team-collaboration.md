# 团队协作

AI 不会消除团队协作，反而会让协作质量更重要。当每个人都能快速产生大量代码时，团队最稀缺的资源变成共享理解、审查注意力、运行反馈和清晰的决策权。

## 团队需要覆盖的责任

以下是责任，不一定对应固定职位。小团队中一人可以承担多个责任，大团队中则应明确分工。

| 责任 | 产出 | 最终负责者 |
| --- | --- | --- |
| 产品意图 | 目标、优先级、接受标准 | 产品或领域负责人 |
| 技术边界 | 架构约束、数据与接口契约 | 技术负责人 |
| 实现 | 代码、测试、文档更新 | 开发者与 Agent |
| 独立验证 | 风险审查、行为验证、证据评估 | 非原始实现者 |
| 发布与运行 | rollout、监控、回滚、事件响应 | 服务或系统 owner |

AI 可以参与每个环节，但关键决策必须能追溯到一个人类责任人。

## 推荐的团队工作流

```text
目标与约束确认
      ↓
任务契约进入 Ready
      ↓
人 + Agent 实现并自验证
      ↓
独立审查高风险假设
      ↓
自动门禁与发布授权
      ↓
生产观察、文档回写与任务关闭
```

## 共享上下文应进入稳定系统

聊天适合探索，不适合充当组织记忆。团队应把不同信息放到与其生命周期匹配的位置：

- 当前系统行为放在代码和 current-state docs；
- 已批准但尚未实现的工作放在 task contract 或 requirement；
- 暂不处理的真实问题放在 backlog；
- 长期有价值的取舍放在 decision record；
- 完整讨论和变更证据留在 Git、PR 与 issue；
- 人员、客户和敏感业务信息留在相应受控系统。

原则是 **repository-native，而不是 repository-only**。

## 审查制度应随风险变化

所有变更都走同样重量的审查，会让小改动变慢，也会让真正危险的改动淹没在流程里。

可以按风险设置层级：

| 风险 | 示例 | 最低要求 |
| --- | --- | --- |
| 低 | 文案、局部样式、无行为重构 | 自动检查 + 作者确认 |
| 中 | 常规业务逻辑、内部接口变化 | 同行 review + 自动化测试 |
| 高 | 权限、支付、数据迁移、公共契约 | 独立领域审查 + 集成验证 + rollout 计划 |
| 极高 | 不可逆数据操作、生产安全边界 | 双人授权 + 演练/回滚证据 + 明确发布负责人 |

风险级别应由影响范围、可逆性和证据难度决定，不由代码行数决定。

## 多 Agent 协作

多个 Agent 并行工作前，应满足：

- 每个子任务有明确 owner、输入、输出和文件/系统边界；
- 共享接口或数据契约先确定；
- 不让多个 Agent 无协调地编辑同一事实源；
- 汇总者负责验证组合后的整体行为，而不是简单拼接输出；
- Agent 之间传递的是可验证 artifact，而不是只有自然语言结论。

并行化最适合彼此独立的检索、测试、迁移分析或模块实现，不适合尚未解决核心语义分歧的任务。

## 团队度量什么

不要把生成代码行数、prompt 数量或 Agent 使用时长当作核心绩效。更有价值的指标包括：

- 从 Ready 到获得生产证据的 lead time；
- 首次审查通过率与返工轮次；
- 未授权 scope expansion 的比例；
- 发布后回退、事故和缺陷逃逸；
- 文档与代码不一致的数量；
- 已达到淘汰条件但仍保留的旧路径；
- 团队成员恢复任务上下文所需时间。

这些指标用于改善系统，不应用来机械评价个人，否则团队会优化数字而不是结果。

## 团队反模式

- 让“最会用 AI 的人”成为所有任务的瓶颈。
- 将 Agent 生成的大 diff 交给审查者承担全部理解成本。
- 把所有 AI 变化都视为低风险，或反过来要求同样重的人工作业。
- 每个人维护自己的 prompt 和隐性规则，没有共享、版本化的工作方式。
- 允许工具自动合并或发布，却没有明确责任人和回滚路径。
- 用更多 Agent 掩盖需求不清、架构耦合或测试反馈太慢的问题。
