# 团队合作：先解开依赖，再增加并行

[English](en/03-team-collaboration.md) | **简体中文**

一个人用 AI 更快完成实现，未必缩短团队的交付时间。若工作仍在等接口、决定和审查，继续启动任务只会增加等待。先看工作卡在哪里，再决定如何分工。

## 按可验证的结果拆任务

产品、设计和工程先共同明确用户问题、成功条件和不做什么。然后把工作拆成可以独立演示、验证或发布的增量，而不只是“前端一张票、后端一张票”。

每个增量写清四件事：结果负责人、执行者、验收方式、集成负责人。低风险工作可以由一个人兼任；高风险工作安排独立验证。共同使用[完成深度](04-task-management.md)，避免一个人的“完成”成为另一个人的待办。

## 分清四种依赖

| 卡点 | 处理方法 |
| --- | --- |
| 接口或数据格式未定 | 先约定字段、错误语义、版本和验收样本；双方再对契约实现。 |
| 必须按顺序改变数据或运行状态 | 先扩展兼容能力，再迁移，最后收缩旧路径；分别验证恢复条件。 |
| 共用设备、环境、账号或审查者 | 显式排队、预留容量；重复出现时考虑自助环境。 |
| 产品或风险决定未定 | 指定决定者和期限；超时升级。只有事先批准的默认方案才能继续。 |

不确定的语义需要先决定。多个 Agent 同时猜测，只会产生不同版本的答案。

## 一个跨应用的拆分例子

以下是 POS 与员工端协作的示意，不是一次具体发布记录。

```text
共同确定：请求、响应、错误、最低 POS 版本
                      ↓
员工端：对样例/假服务实现 ──┐
POS 端：实现真实接口 ──────┤ 真实联调 → 联合验收 → 按版本顺序发布
```

假服务让界面和边界测试提前开始，不能替代真实联调。接口成功、超时和旧版本不支持时的行为，都要在契约中写清。若新员工端依赖新 POS，发布顺序仍然存在；需要兼容路径或开关时，同时记录退出条件。

用[依赖与切片地图](../templates/dependency-map.md)记录阻塞点、解除责任人和集成时间。共享 schema、配置或核心文件指定本轮修改负责人，减少同时编辑造成的冲突。

## 集成越晚，局部完成越不可信

保持小批量和短分支，尽早把真实实现接起来。每个切片自测通过后，仍要有人验证组合行为。审查分工可以很简单：

- 自动化检查格式、类型和已知规则。
- 领域审查者检查验收、失败路径及数据影响。
- 有相应权限的人决定发布和残余风险。

AI 可以协助每一层，但测试通过和 AI review 都不能替代尚未完成的领域判断。

## 同步时只聚焦阻塞与结果

每次同步问：哪个任务停住了、卡在哪个接口或决定、谁能解除？等待计入任务年龄；超过约定期限就调整范围、拆分或升级。

发布前确定观察信号、停止条件和负责人。发布后比较结果与目标，把偏差转成测试、文档或后续任务。若等待长期集中在团队边界，继续看[组织架构](05-organization-structure.md)；若集中在审查队列，先限制[在制任务数](04-task-management.md)。
