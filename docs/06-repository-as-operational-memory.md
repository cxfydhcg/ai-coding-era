# 仓库即交接：换人或换 Agent 都能继续

[English](en/06-repository-as-operational-memory.md) | **简体中文**

仓库要保存足以继续工作的状态：为什么做、准备做什么、做到哪里、卡在哪里、下一步怎么验证。聊天用于讨论，决定和进度及时写回仓库；不能只留在会话、私人笔记或某个 Agent 的记忆中。

## 给接手者一个入口

从 README 和助手入口指向同一份任务索引，再链接到各任务或需求记录。沿用已有索引即可，不另建一套平行看板。索引负责导航，任务记录保存唯一的当前状态：

| 接手者需要知道 | 记录什么 |
| --- | --- |
| 做什么，为什么 | 目标、范围、验收和已确定的取舍。 |
| 做到哪里 | 已完成、进行中、未开始；区分已实现与已验证。 |
| 从哪里继续 | 可访问的分支、提交或 PR，以及下一条具体动作。 |
| 什么挡住了工作 | 阻塞、待决定问题、负责人和权限边界。 |
| 如何确认结果 | 环境准备、验证命令、结果、证据位置和更新时间。 |

完成一个阶段、改变决定、遇到阻塞或暂停前，由当前执行者更新这份记录，覆盖旧状态，不追加聊天流水账。交接时确保代码和记录已保存到接手者可访问的分支；本机未提交的改动不算已经交接。

接手者先读入口，再核对分支、diff 和验证结果，记录自己接手后继续下一步。记录与代码不一致时先修正状态；多人并行时明确各自负责的任务，避免重复执行。客户、人员、密钥和敏感运营资料仍在受控系统中，仓库保留必要的获取与验证入口。

**交接验收：不给原聊天，让有相应权限的新成员或新 Agent 找到目标、当前状态、下一步和验证方式。找不到，就说明仓库还没保存完整。** [任务模板](../templates/task-contract.md)包含可直接填写的进度区。

## 四类记录，回答四个问题

| 位置示例 | 回答什么 | 什么时候更新 |
| --- | --- | --- |
| `docs/<feature>/` | 现在如何工作？ | 行为变了就重写。 |
| `docs/change_log/` 或已有 ADR | 为什么这样改或这样设计？ | 保留仍有用的取舍；长期决策不按短期记录清理。 |
| `BACKLOG.md` | 什么已知问题暂不处理？ | 写证据、延后原因和修法；验证后关闭。 |
| `requirement_doc/<series>/` | 协调工作按什么契约实现，进展到哪？ | 区分提议与批准，写明验收和门禁；更新进度与下一步。 |

目录名称可以不同，职责要清楚。实现、测试和 schema 帮助核实当前行为；声明为权威的外部契约则约束实现。发现冲突时查明原因，修正错误的一方，不能默默挑一个相信。

## 信息随工作移动

```text
发现问题 → 记录延后工作 → 需要协调时形成契约
→ 实现与验证 → 更新当前行为和理由 → 发布观察 → 退役旧记录
```

提升为需求时转移原 backlog 的证据，不维护两份任务正文。已完成 spec 可以暂时保留验收和发布证据，但不替代当前文档。Git 与 PR 保存完整历史，日常入口只保留仍会影响决定的内容。

## 自动化能做多少，就说明多少

路径查询能找到相关 backlog；检查器能发现断链、索引缺项和漏改的契约文档；巡检能根据确定规则提出清理建议。它们不能证明产品行为正确，也不能从版本 tag 推断全部设备已升级。

把工具不执行的步骤写进助手入口。复制 skill 不等于安装 hook；提醒不等于强制执行。多助手共用规则时保留一个可编辑来源，其他副本生成并检查一致性。

## 临时机制也要有去处

为临时分支记录用途、依赖者、移除条件和验证方式。发布后仍可能存在旧客户端、离线队列或可恢复的旧备份；门禁满足后再做删除变更，不能按年龄直接清理应用代码。

具体目录、标记和删除规则见[记录生命周期实践](08-record-lifecycle.md)。先用一项真实工作验证能否找到上下文，再增加自动化。
