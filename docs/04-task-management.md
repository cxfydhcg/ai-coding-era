# 任务管理：控制开始，明确完成

[English](en/04-task-management.md) | **简体中文**

我把任务看成一个有负责人、有边界、能验收的结果。一段 Agent 对话只是执行尝试；目标、进度、阻塞、下一步和证据都保存在仓库的任务记录中。换人或换 Agent 时，从这份记录继续，具体见[仓库交接](06-repository-as-operational-memory.md)。

## 先选值得做的工作

优先考虑用户影响、紧迫性、风险降低，以及完整交付的成本。成本包含理解、实现、验证、协调和发布。“AI 很快能写完”不够成为优先理由。

| 发现的工作 | 去向 |
| --- | --- |
| 在当前授权范围内，且能验证 | 现在修复。 |
| 真实、可独立执行，但暂不处理 | 记入 backlog，写证据、延后原因和修法。 |
| 需要共享接口、阶段、发布或产品决定 | 建需求契约，标明哪些决定尚未批准。 |
| 证据不足 | 限时调查，写清要回答的问题。 |
| 已失效或不再值得做 | 删除或关闭，并留下原因。 |

一个任务开始前，至少写清目标、范围、约束、验收和负责人。复杂任务再补依赖、权限与发布计划，使用[任务模板](../templates/task-contract.md)。

## 用最少的状态看见等待

```text
待明确 → 可开始 → 实现中 → 验证中 → 待发布/观察 → 完成
```

可开始意味着验收清楚、关键依赖有安排。完成意味着达到约定的验证深度。小任务可以合并状态；设备验证或生产观察没做，不能通过改列名让它消失。

限制已开始但未完成的任务数（WIP）。验证队列满时，优先审查、联调和解除旧任务阻塞。并行开几个 Agent 不等于业务上完成几件事。

同时显示任务已开始多久、等待什么、谁能解除。积累历史后，用周期时间估计交付区间，而不只看工时。WIP、吞吐量、任务年龄和周期时间是 [Kanban Guide](https://kanbanguides.org/the-kanban-guide/) 定义的基本流动指标；具体上限与升级期限由团队试验。

## 完成深度：先约定，再验收

下面是本系列采用的检查方法，不是行业统一标准。层级表达任务承诺，不是给团队打分。

| 深度 | 需要证明什么 | 证据例子 |
| --- | --- | --- |
| D0 能演示 | 功能出现，有反应。 | 演示；不能单独证明正确。 |
| D1 主路径正确 | 典型输入满足验收。 | 行为测试或可复现验证。 |
| D2 边界与失败正确 | 相关异常、权限、重复和并发得到处理。 | 边界测试、故障注入或探索记录。 |
| D3 能在真实系统运行 | 数据、依赖、兼容、性能与恢复满足需要。 | 真实联调、预生产或小范围发布。 |
| D4 结果已观察 | 用户或系统结果得到验证，临时机制已处理。 | 生产证据；删除记录或有负责人和门禁的保留项。 |

原型可以约定只做到 D1。面向真实用户的功能通常需要 D2、D3；支付、权限和迁移还应安排后续观察。深度由后果与可逆性决定，一次性删除脚本也可能是高风险任务。

如果承诺 D3，就不能把没做的集成测试移到 backlog 后宣布完成。改变承诺需要明确决定；不适用的检查则直接标明理由，不必制造无用任务。

## 审查优先找四种遗漏

- **状态遗漏：** 成功之外，空、错、超时、重试和部分成功如何表现？
- **视角遗漏：** 普通用户、不同租户、旧数据和真实数据量是否成立？
- **证据循环：** 测试是否只是复述实现？预期结果来自哪里？
- **交付遗漏：** 联调、配置、诊断、恢复与临时路径有没有负责人？

换一个 Agent 会话可以帮助发现不同问题，但独立证据仍要来自契约、真实样本、领域判断或独立计算。按风险取用[完成检查表](../templates/completion-depth-checklist.md)，无需逐项套用。

## 权限与评价

任务中写明 Agent 可连续完成什么，哪些新决定需要授权，以及谁能发布。权限跟动作的后果有关，不由模型名称决定；已授权的步骤不重复审批。

看流程是否改善，先追踪交付时间、等待、返工、发布缺陷和用户结果。不要用代码量、调用数或关单数单独评价个人；[SPACE 研究](https://www.microsoft.com/en-us/research/publication/the-space-of-developer-productivity-theres-more-to-it-than-you-think/)也强调生产力不能由单一活动指标代表。
