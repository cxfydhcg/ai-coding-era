# 组织架构：让责任和交付能力对齐

[English](en/05-organization-structure.md) | **简体中文**

当 AI 缩短实现时间，组织仍可能卡在跨部门等待、关键人审查和发布协调。先观察这些瓶颈，再调整责任与服务边界；不必先重画组织图。

以下是设计建议，实际效果要在自己的组织中验证。

## 围绕长期负责的领域组织工作

一个领域需要有人持续负责产品行为、代码、数据、运行和后续维护。团队内可以有不同专业分工，但不能让交接之后的结果无人负责。个人负责具体任务，Agent 承担执行，长期系统保留明确的人类负责人。

例如，订单团队应能判断订单变化的用户影响，完成常规修改与验证，并处理上线后的故障；不应每次都重新寻找谁负责接口、日志和发布。

## 哪些集中，哪些留在领域

| 共享建设 | 领域内决定 |
| --- | --- |
| 模型接入、身份、权限和审计 | 用户目标、优先级与产品行为 |
| 开发环境、CI、发布与监控能力 | 任务范围、验收与领域测试 |
| 数据使用、安全和供应链规则 | 当前文档、问题记录与兼容约束 |
| 通用评估、成本和支持工具 | 授权范围内的发布、生产观察与维护 |

共享能力应该减少重复劳动和等待。若每次正常使用都需要提工单、找熟人，先改善自助入口与服务承诺。领域团队也不能因为自治而绕过共同的数据或生产规则。

## 按需要补能力，不按人数套组织图

[Team Topologies](https://teamtopologies.com/key-concepts)提供了四种能力视角：领域交付、内部平台、短期赋能、专业子系统。可以用来检查缺口，不必建立四个部门。

- 小团队可以由同一人兼任，用模板和自动化共享能力。
- 多个团队反复解决同一问题时，再考虑设立平台责任。
- 临时缺技能时，用有期限的结对或辅导，达到目标后退出。
- 专业知识确实难以分散时，保留专门团队并提供稳定接口。

团队之间写清是共同探索、自助服务，还是短期辅导，以及何时结束密集协作。这借用了上述框架的交互分类；具体边界仍需结合系统设计。

## 一页说明团队边界

每个团队公开：负责什么系统和结果、提供什么服务、如何请求支持、哪些决定可以自主做、接口如何演进，以及故障找谁。Agent 可访问的数据和操作权限也应有清晰入口。

重大变化先协作确定新边界；边界稳定后尽量转成可直接使用的服务，减少每次都重新协调。

## 从反复出现的阻塞找改进点

| 现象 | 先检查什么 |
| --- | --- |
| 每次发布都等多个团队 | 接口是否过度耦合，发布责任是否分散。 |
| 大多数问题只能找一个人 | 知识、文档和决定权是否过度集中。 |
| 审查积压但仍不断开新任务 | 在制任务上限是否超过验证能力。 |
| 团队花很多时间维护无关基础设施 | 是否需要共享平台，或删除不必要复杂度。 |
| AI 反复犯同类错误 | 契约、局部规则与检查是否缺失或冲突。 |

管理者优先解决这些障碍：明确优先级、保护审查容量、补齐反馈和责任。用等待、返工、故障及团队负担判断调整是否有效，不以 AI 使用率证明组织已经进步。
