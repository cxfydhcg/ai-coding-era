# 组织与团队结构

AI coding 不只是给每个工程师增加一个工具。它改变了组织中的稀缺资源：实现能力变得更充足，清晰决策、领域知识、验证能力、平台可靠性和生产责任变得更重要。

## 组织设计原则

### 1. 以业务领域和结果组织团队

领域团队应拥有从目标、实现到生产结果的闭环，而不是把“写代码”集中交给一个 AI 团队。理解客户和系统边界的人，需要对最终行为负责。

### 2. 集中建设通用能力，分散承担产品责任

适合集中建设的能力包括 Agent 运行环境、模型接入、安全策略、评估框架、开发工具、可观测性和成本治理。具体产品行为、优先级和发布风险仍由领域团队负责。

### 3. 执行可以弹性扩展，责任必须明确到人

一个任务可以由多个 Agent 和自动流程执行，但必须有一个 human accountable owner。矩阵中的“大家都负责”通常意味着关键时刻无人负责。

### 4. 让验证能力成为一等平台能力

如果团队可以快速生成实现，却要等待数天才能获得测试环境、数据或生产反馈，AI 只会把更多变化堆在瓶颈前。平台投资应优先缩短可信反馈时间。

## 推荐的三层结构

```text
公司级治理与风险边界
          ↓
AI / Engineering Platform
          ↓
拥有业务结果的领域团队
```

### 领域团队

负责：

- 产品目标和优先级；
- 领域模型、业务规则和服务边界；
- 任务契约、实现与审查；
- 发布、运行、事件响应和旧能力淘汰；
- 把领域知识沉淀为可检索 artifact。

Agent 应嵌入领域团队的日常流程，而不是作为外部“代码工厂”。

### AI / Engineering Platform

负责：

- 统一的 Agent 运行环境、身份和权限；
- 模型与工具接入、成本和可靠性；
- repository 模板、CI、测试基础设施和评估；
- 安全的 sandbox、secret 管理和审计记录；
- 可复用 skill、上下文检索和工程护栏；
- 培训、咨询与内部实践传播。

平台团队提供 paved road，但不替领域团队决定产品行为。

### 公司级治理

负责定义少量不可协商的边界，例如：

- 哪些数据可以发送给哪些模型和供应商；
- 哪些动作需要人工批准或双人授权；
- 代码、模型输出和审计记录的保留政策；
- 第三方许可、知识产权和供应链要求；
- 高风险领域的发布与事件上报标准。

治理应尽可能通过工具和默认配置落地；只有政策没有机制，会迫使每个团队重复解释。

## 一个典型领域团队

团队规模应由领域复杂度决定，而不是固定数字。一个 4–8 人的跨职能团队可以包含以下责任：

- 1 个 outcome owner：拥有问题、优先级和成功标准；
- 1 个 technical owner：拥有系统边界和关键技术取舍；
- 多个 product engineers：与 Agent 一起实现、测试和运行；
- shared design / data / QA / SRE 能力：按实际产品需要嵌入或服务多个团队。

这不是要求增加职位，而是确保每项责任有人承担。小公司中，两三个人也可以覆盖全部责任。

## 任务层面的责任模型

对中高风险任务，至少区分四种责任：

| 角色 | 责任 |
| --- | --- |
| Accountable owner | 定义结果、批准关键取舍、接受残余风险 |
| Executor | 人与 Agent 共同完成实现和自验证 |
| Independent validator | 检查高风险假设，不依赖原实现者的叙述 |
| Release authority | 决定何时进入生产以及何时回滚 |

低风险任务中一人可以兼任多项；高风险和不可逆任务应避免由同一人或同一 Agent 同时充当实现者与唯一验证者。

## 不建议的组织方式

### 独立 AI 代码工厂

一个中央团队接受需求并用 AI 交付代码，会切断领域知识、实现和生产责任。短期看吞吐量很高，长期会积累返工与 ownership 缺口。

### 只采购工具，不改变反馈系统

给所有人购买 AI 工具，却不改善测试、文档、环境和任务质量，通常只会生成更多难以审查的变化。

### 用 AI 使用率衡量绩效

这会鼓励不必要的生成，惩罚谨慎判断。组织应衡量结果、质量、反馈时间和可维护性。

### 规则全部中心化

公司级规则过多会失去领域语境并快速过时。全局只保留真正跨团队的边界，领域规则应靠近其代码和 owner。

## 管理者的新工作重点

- 提高问题定义和优先级决策的质量；
- 识别审查、测试、环境和发布中的真实瓶颈；
- 让责任、权限和升级路径清楚；
- 为领域知识、文档维护和技术债淘汰预留容量；
- 建立允许试验但限制风险半径的环境；
- 关注系统性指标，不用个体产出数字驱动局部优化。
