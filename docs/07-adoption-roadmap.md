# 采用路线图

[English](en/07-adoption-roadmap.md) | **简体中文**

AI-native 开发不需要一次完成组织重构。更稳妥的做法是从一个团队、一个 repository 和几类高频任务开始，逐步建立可验证的反馈循环。

## 阶段 1：建立安全边界

目标：允许团队使用 AI，同时清楚什么不能自动做。

- 定义数据、secret、第三方服务和代码许可边界；
- 明确破坏性操作、生产修改和对外行动的授权规则；
- 要求每个 AI 参与的变化能够追溯到人类 owner；
- 选取低风险、容易验证的任务作为起点。

完成信号：团队知道何时可以自主继续，何时必须暂停并升级。

## 阶段 2：整理 repository 上下文

目标：让人和 Agent 能快速理解当前系统与局部规则。

- 为关键领域补充短而准确的 current-state docs；
- 将长期规则靠近相关代码，避免一个无限增长的总说明；
- 区分当前行为、未来计划、延后工作和历史原因；
- 清理明显过期、冲突和重复的文档。

完成信号：新参与者不依赖原作者口述，也能定位权威信息。

## 阶段 3：标准化任务契约

目标：减少 Agent 对意图和范围的猜测。

- 在中高风险任务中使用统一模板；
- 定义 Ready、Done 和 scope expansion 规则；
- 建立 fix now / backlog / requirement 路由；
- 使用稳定 ID 连接任务、PR、发布证据和决策记录。

完成信号：审查争论更多集中在真实取舍，而不是补问任务背景。

## 阶段 4：自动化验证与策略

目标：让生成吞吐量不超过验证吞吐量。

- 缩短单元、集成和端到端测试反馈；
- 把格式、链接、schema、权限和发布策略变成自动检查；
- 对高风险变化增加独立验证与 rollout 证据；
- 让 Agent 报告已验证事实、推断和未验证假设。

完成信号：大多数常见错误在进入人工审查前已经被发现。

## 阶段 5：连接生产证据与淘汰

目标：从“代码合并”扩展到完整生命周期。

- 把发布版本、运行指标、迁移状态和旧流量观察连接到任务；
- 给临时兼容层和 feature flag 设置 owner 与 removal gate；
- 定期审查达到淘汰条件的代码、文档和流程；
- 将生产偏差写回 current-state docs 和验证体系。

完成信号：团队能够用证据安全删除旧路径，而不是无限保留“以防万一”。

## 试点建议

选择一个满足以下条件的领域：

- 业务 owner 明确；
- 有稳定但不完美的自动化测试；
- 任务量足够观察变化；
- 风险可控且存在真实维护成本；
- 团队愿意记录基线并持续复盘。

先运行 6–12 周，不要急着把一个试点结论推广到所有类型的软件。

## 建议指标

| 维度 | 指标示例 |
| --- | --- |
| 速度 | Ready 到 production evidence 的中位时间 |
| 返工 | review 轮次、重新打开任务比例 |
| 范围 | 未授权 scope expansion 比例 |
| 质量 | 缺陷逃逸、回滚、事故和恢复时间 |
| 上下文 | 开始有效工作前的查询与人工解释次数 |
| 文档 | 过期链接、代码/文档冲突、重复事实源 |
| 生命周期 | 达到 removal gate 后的旧代码存活时间 |
| 经济性 | 每个可信交付结果的模型、计算与人力成本 |

在引入变化前先记录基线。指标用于识别瓶颈和学习，不用于追求表面上的 AI 使用率。

## 每月复盘问题

1. 哪些任务因为定义不足而产生了最多返工？
2. 生成、审查、测试、发布和生产反馈中，当前瓶颈在哪里？
3. Agent 最常做出的错误假设是什么，能否通过局部上下文或自动检查修复？
4. 哪些规则已经失效或制造无价值流程？
5. 哪些临时机制已经达到删除条件？
6. 哪些高风险决定缺少明确责任人或独立证据？

真正的成熟不是自动化比例最高，而是团队能以更低的认知成本，持续交付可理解、可验证、可运行、也可安全删除的软件。
